## 출력 구성요소의 통제 비교

같은 v2/v4 입력 경로도 실행별 차단 F1이 달라져 출력의 효과를 분리하기 어렵다. `jh_output_replay.py`는 `jh_full_v4/v4_1`의 **자체 입력 예측**을 고정하고, 공개 대화와 BM25 top1 검색을 재현하여 후보의 출력 검사만 호출한다. 예측 category/decision이 보존되는지 검사한다. 정답 입력 라벨은 상태 생성에 쓰지 않는다. 이 값은 출력 진단이며 전체 HTTP 평가나 비공개 점수로 취급하지 않는다.

```bash
.venv/bin/python experiments/jh_output_replay.py --source experiments/.cache/jh_full_v4/v4_1 --variant jh_v4_safety --name safety_fixed_1 --workers 16
```

고정 입력 출력 진단 1회: 원래 v4 87.79, `jh_v4_safety` 88.29. 두 실행 모두 입력 F1 0.8696 / 범주 정확도 0.8721로 동일하다. 그러나 같은 근거 알고리즘도 grounded 0.9070→0.9186, span 0.7787→0.8122로 흔들렸고, 안전성은 0.9767→0.9651로 낮아졌다. 0.50점 상승을 안전 검사 개선으로 해석하지 않는다. 원래 end-to-end v4의 89.17과도 출력 재실행 변동이 있으므로 작은 차이는 반복 확인한다.

## 자체 분류기 탐색 — 미채택

공개 400건으로 문자 TF-IDF + logistic regression을 처음부터 학습해 5-fold 교차검증했다. 마지막 질문의 문자 유사도 0.82 이상을 묶은 375개 그룹을 나눴고, 각 fold의 어휘/모델은 학습 fold로만 적합했다. 마지막 발화 단독/이력 추가 × C 0.3/1/3/10을 비교했다.

최고 범주 정확도는 71.75%, macro F1 0.6768, block F1 0.6667이었다. 높은 확률 영역도 표본이 작아 배포하지 않는다. `jh_classical_cv.py`의 재실행 결과가 첫 탐색과 정확히 일치했다. scikit-learn 1.9.1을 선택 연구 의존성으로만 기록했으며 모델 파일은 서버에 넣지 않았다. 기록은 `experiments/.cache/jh_ml_cv/`에 있다.

검색 후보만 오프라인으로 비교했을 때, 정답 근거가 있는 tutor 119건의 top1 적중은 기존 조각 BM25 108, 섹션 전체 BM25 106, 마지막 발화만 섹션 검색 93, 두 순위 결합 107이었다. 단순 검색 교체는 채택하지 않는다.

## 후속 검증 순서

첫 `jh_full_voted_64`는 전체 **87.19** (tutor 86.12 / guard 88.27), HTTP·형식·채점 오류 0이었다. 내부 실패는 material timeout 2 / parse 1이다. 다만 수집 도구가 `asyncio.to_thread` 기본 풀을 사용하여 `--workers 64`만큼 실제 HTTP를 동시에 전송하지 못했다. p95 30.373초 / 최대 35.775초에는 이 클라이언트 대기까지 섞였다. 점수와 원본 기록은 보존하지만 **실제 동시성 64 검증으로 인정하지 않는다**. 이전 workers 16 결과도 호스트 기본 풀 크기에 따라 전송 제한을 받았을 가능성이 있다.

후속 runner는 요청한 workers만큼 명시적 ThreadPoolExecutor를 사용한다. 40개 전송이 동시에 시작되어야 풀리는 barrier 회귀 테스트와 응답 중복 거부 테스트를 추가했다. 테스트 103개 통과. 평가기의 점수 계산·판정 프롬프트는 바꾸지 않았다. 수정 후 원래 v4와 voted를 같은 실제 동시성 64로 재검증한다.

호스트 기본 스레드 수를 직접 확인한 값은 16이다. 따라서 앞선 workers 16 비교는 유지하며, 최초 voted의 workers 64 표기만 실제 HTTP 최대 16으로 정정한다. `jh_summarize.py`는 완료된 200건 이상 실행을 집계하며 요청 workers와 실제 HTTP 상한을 별도로 기록한다. 원본 응답과 프롬프트는 집계 파일에 넣지 않는다.

`3bb7168`의 `jh_reasoned`: 다수결 대신 block·other에 medium 추론을 사용한다. 제공 프록시의 2000 비스트리밍 제한을 피하기 위해 내부 API를 streaming 4000으로 소비하되, 외부 HTTP 응답 형식은 동일하다. 전체 스트림을 포함한 12초 제한과 연결 정리 테스트를 추가했다. material·출력 검사·답변 생성은 calibrated와 같으며 먼저 작은 실제 API 검증부터 진행한다.

## 중단 복구

`971e15a`부터 공개 채점 호출의 입력 해시와 판정 결과를 실행 폴더의 `judge.jsonl`에 저장한다. 프롬프트·모델 호출 인자를 바꾸지 않는다. 같은 실행의 같은 채점 입력에만 결과를 재사용한다. 완료된 평가를 좋은 점수가 나올 때까지 다시 뽑는 기능이 아니다.

응답 400건 수집 이후 채점이 중단됐으면 다음처럼 재개한다.

```bash
.venv/bin/python experiments/jh_resume_score.py experiments/.cache/jh_RUN/VARIANT_1
```

평가기 해시·모델·공개 ID·문항 수가 맞아야 재개하며, 이미 완성된 결과는 덮어쓰지 않는다. 재개는 실행별 `result.json`을 만들며 상위 `summary.json`을 재작성하지 않는다.
